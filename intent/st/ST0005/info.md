# ST0005: Utilz liberator: a checkout or Homebrew, per sleeve

## Objective

Molt's utilz liberator gets Utilz the way each sleeve declares, from a dev checkout or from Homebrew, and its verdict names the utilz that PATH actually runs. Molt's Homebrew check is one helper, shared with the intent liberator, and it reports a formula that Homebrew no longer trusts.

## Context

On 20 Oct kovacs-sysadm reported that `molt doctor` on kovacs says `utilz: repo not found`. hv made kovacs brew-only for Utilz and Intent on 19 Oct: the dev checkout and its 16 `~/bin` links were removed, and Utilz 2.14.1 comes from the `matthewsinclair/utilz` tap. The liberator knew one model, a checkout at `MOLT_UTILZ_HOME` that it linked into `~/bin` and upgraded with `git pull`. hv rejected `enabled = false` as a fix, and ruled on 20 Oct that each sleeve chooses between checkout and brew; kovacs is brew.

The same check was wrong on rhadamanth in the other direction. A login shell there runs Homebrew's utilz 2.14.1 from `/opt/homebrew/bin`, ahead of the checkout links in `~/.local/bin`, and the liberator reported utilz healthy because it asked whether its link resolved, never which utilz ran. That is the defect ST0004 fixed for intent on gyges.

Decided with hv on 20 Oct: a Homebrew install is upgraded by `molt maintain`'s `brew upgrade`, not by `molt upgrade`, because the utilz formula compiles Rust; and Molt trusts exactly the formula it installs, saying so, under Homebrew 7.0.10's trust gate. Measured on rhadamanth against an empty trust store: an install by full name trusts the formula itself, a short name is refused, and a plain `brew upgrade` skips any installed formula from an untrusted tap with a warning and exit 0. A formula installed before the gate arrived therefore goes un-upgraded while `molt maintain` reports success.

Not in scope: making the brew liberator run on Linux, so that `molt maintain` upgrades brew packages on kovacs; and the manifest's `depends` key, which no Molt code reads.
