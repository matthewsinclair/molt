Found at Molt 1.2.0's rollout, 30 Oct 2026, on kovacs (kovacs-sysadm) and on rhadamanth.

When the env check fails only because the GUI session does not hold a published pair, its own remedy says that only a login clears it. That session is launchd's GUI domain on macOS (issue 0072) and the systemd user manager on Linux (issue 0076). On macOS the remedy is the next login or a bootstrap of com.molt.env, and on Linux it is to log out and back in. Doctor's enabled-liberator check then reports env as "not installed", and closes with its fixed hint (lib/molt.sh, cmd_doctor): "Run `molt resleeve` to install, or `molt list` for status." A resleeve renders the same files again and changes nothing the session holds, so the hint sends the reader to a step that cannot clear the finding. kovacs-sysadm read it that way on kovacs, where the manager held a PATH without ~/.local/bin and with /snap/bin twice until hv's GNOME re-login. rhadamanth showed the same, with launchd lacking INTENT_INSTALL_PREFIX because the plist is newer than the last login.

Ask: doctor names `molt resleeve` only where a resleeve would clear what failed. When the only finding is one the env check says a login clears, it names env as published but not yet in the session, and leaves the remedy to the env check's own line. Doctor still fails on it, since GUI apps really do not get the value (issue 0059).

Not in 1.2.0: hv ruled one release today, with no new work for its own sake (vc decisions 36 and 38).
