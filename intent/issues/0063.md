## What changes (hv's ruling, 25 Oct 2026, through intent-ic; devbin's contract amendment A3 to T4)

hv: "That info is idiotic. Why would that ever be necessary when you can just type of which it!?" The ` at <root>` tail comes off every tool's version line. Contract A3 (devbin-vc's draft, sha256 b19ffcb92d11...; molt-vc SAME): the line is `<tool> <version> (<tree>, <sha12>[+dirty])`, and the unknown form is `<tool> <version> (dev, unknown)`. The line names no path: `command -v <tool>` says where the running copy lives. A reader reads up to the closing parenthesis and ignores what follows. Molt is a script tool, so it appends no provenance word.

Today `molt --version` prints `molt 1.0.1 (brew, fb0d8ff5d15d) at /opt/homebrew/opt/molt/libexec`.

## Spec (vc, 25 Oct 2026)

- `molt_version_line` (lib/install.sh) prints `molt <version> (<tree>, <sha12>[+dirty])`, or `molt <version> (dev, unknown)`. It stays the one writer. Its comment shows the new shape.
- Every caller keeps calling it: install's "Installed:" line, `molt use`'s report (lib/install.sh and liberators/local-bin.sh, "<link> serves <line>"), doctor, and bin/molt's `version`. None of them adds a path back. A check that fails about a path names that path itself, as A3 says.
- bin/molt's help line for `version`, README.md's, and the two guides (bootstrap-runbook, getting-started) drop "and root" and the ` at ...` example.
- test/install.bats' pins (the opt, dev, +dirty, unknown and brew lines) pin the new whole line, and a test asserts that no ` at ` follows the parenthesis.
- Any Molt code that reads another tool's version line (eg the intent, utilz, gtools liberators) reads up to the closing parenthesis only, so it accepts both shapes while the other tools change.
- Lands only after all four VCs have sent SAME on A3. The full suite runs under Homebrew bash and /bin/bash, plus the critic leg.
