## What happened

Molt 1.4.6's first local gates leg died after 1191 seconds at release commit a7456a33, with:

```
release: gates: a gate changed the tree: intent/whiteboard/vc/board.json, intent/whiteboard/vc/wip.md -- the gates examine the release commit and must not write to it
```

No gate wrote those files. They were already uncommitted before the run started: vc had refreshed its whiteboard focus line and then held the files rather than committing them, on the rule against writing to the shared tree during another node's slot. The candidate CI was green on the same sha, and the full bats run produced zero `not ok` lines, so the only thing the leg found was two modified files that had nothing to do with the release.

The resume, after those two files were committed, was green at f2d262767020 and v1.4.6 released.

## Why it matters beyond one run

Molt's checkout is shared by up to four Claude sessions and hv. Every `intent wb` verb writes `intent/whiteboard/<node>/board.json` and `wip.md`, and `pickup` does so on every session boot while reading like a read and merely moving a heartbeat. So "some node's board is uncommitted" is the ordinary state of this checkout, not an aberration, and a release leg that requires a globally clean tree is one routine boot away from burning a full gate run.

The remedy the run names, fix what the row names, is also awkward here: the paths belong to another node, and the whiteboard's single-writer rule means no other session may commit them.

## Two separate defects

**1. The clean-tree check is scoped to the whole tree when it only needs the release commit's own content.** What the gates must know is that what they test is what the release commit holds. They currently assert something much broader, which is that nothing anywhere in the working tree is uncommitted.

Prior art for the narrower shape is in this estate: Webber's `bin/build-app` runs `status --porcelain` against the app's declared input paths at line 206 and against `native/ios` at line 236, so a peer's whiteboard write cannot fail a Webber build. Worth citing honestly: that scoping was written because the app's build inputs are what gets stamped, and immunity to a peer's tree write fell out of it. It is prior art for the shape, not for the rationale.

**2. The message asserts a cause that was false.** "a gate changed the tree" is a claim about causation. Here the files were dirty before the first gate ran, and a reader who trusts the wording goes looking for a writing gate that does not exist. Something closer to "the working tree does not match the release commit: <paths>" would be true, would point at the actual fix, and would not send the next person hunting.

## Cost

1191 seconds of gate run, one candidate push and deletion, and roughly half an hour of wall clock on a cut hv was waiting on.
