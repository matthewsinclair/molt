## What happens (rhadamanth, 25 Oct 2026; found read-only by conflab-ic, confirmed by vc)

`~/Library/LaunchAgents/com.molt.env.plist`, rendered by `_molt_env_plist_text` in `lib/env.sh`, runs ONE `/bin/launchctl setenv` carrying every pair: CLAUDE_CONFIG_DIR, GTOOLS_INSTALL_PREFIX, UTILZ_INSTALL_PREFIX and PATH. `launchctl setenv` takes one key and one value. In gui/501 only the first pair is set: `launchctl getenv CLAUDE_CONFIG_DIR` answers, while `getenv` of GTOOLS_INSTALL_PREFIX, UTILZ_INSTALL_PREFIX and PATH is empty. UTILZ_INSTALL_PREFIX has been in the plist since ST0008 WP05 and has never reached a GUI app, so this predates today's GTOOLS_INSTALL_PREFIX.

The function's comment states the wrong contract ("one launchctl setenv, which takes every pair").

Effect: every app launchd starts (the Dock, Xcode.app, Claude's desktop app, editors) gets launchd's bare PATH, without `~/.local/bin` or `/opt/homebrew/bin`, and none of the install prefixes. Xcode build phases that call a tool by bare name fail (Conflab's coming BuildInfo phase builds a cargo stamp tool), as do hooks and MCP servers named by bare name. `molt doctor` and the env liberator's check pass, because they compare the plist's text with what molt would render, never what launchd holds.

## Spec (vc, 25 Oct 2026)

- **One setenv per pair.** `_molt_env_plist_text` stays the one writer of the plist. Its ProgramArguments become `/bin/sh -c '<script>'`, where the script runs one `/bin/launchctl setenv <name> <value>` per pair, each word quoted so a value holding spaces, `$` or quotes reaches launchd byte for byte. No pair keeps `/usr/bin/true`. Correct the comment.
- **The check asks launchd, not only the file.** On macOS, the env liberator's check (and doctor's) also compares `launchctl getenv <name>` with each published value, and names each pair launchd lacks, saying it takes effect at the next login (or `launchctl bootstrap gui/$(id -u) <plist>`). The check reads only, and never runs setenv itself.
- **Nothing runs setenv during build or test.** Tests render the plist and run its script with a stub launchctl first on PATH, asserting one call per pair with exact argv, including a value with spaces and one with a quote. They never call the real launchctl. Each new test must be red with the change reverted. Run the full suite under Homebrew bash and /bin/bash 3.2, plus shellcheck.

## As built (cc, 25 Oct 2026; merged by vc at 9da1abd and pushed)

- `lib/env.sh`: `_molt_env_plist_text` is still the one writer of the plist. Its ProgramArguments are `/bin/sh`, `-c` and a script of `launchctl setenv 'NAME' 'value';`, one per pair. Each word is single-quoted by `_molt_env_sh_quote`, and the script is XML-escaped by `_molt_env_xml_text`. With no pairs it runs `/usr/bin/true`. launchctl is named bare, not `/bin/launchctl`, so a test's stub on PATH takes the call. The header comment is corrected: nothing sets anything through launchctl except the agent at login.
- `lib/env.sh`: a new `molt_env_report_launchd` runs on macOS only and only reads. It runs `launchctl getenv` for each pair and names each pair launchd lacks or holds with another value, or whose getenv failed. Then it says the plist takes effect at the next login, or now with `launchctl bootout gui/<uid>/com.molt.env; launchctl bootstrap gui/<uid> <plist>`.
- `liberators/env.sh`: `env_check`, and so doctor, calls it. `env_verify` is unchanged (vc: check only).
- `test/liberators/env.bats`: a stub launchctl first on PATH records each call's argv and keeps a fake launchd store. A faked login runs the plist's script. New tests pin the exact argv per pair, for a value with spaces and one with `'`, `$`, `"`, `&` and `<b>`. They also cover the check reporting missing and different pairs, passing after a login, and calling no launchctl on Linux.
- `test/test_helper.bash`: a do-nothing launchctl goes first on PATH at load, so no test reaches the real one. Without it, molt.bats's doctor, status and list tests reached `launchctl getenv`. `test/liberators/claude.bats` AT012 pins the `/bin/sh` script form.
- Each new assertion fails with its change reverted.
- In the full suite under Homebrew bash and /bin/bash 3.2, all tests pass, and a tripwire launchctl behind the stubs recorded no call. shellcheck finds nothing new, and `intent critic shell` finds nothing at warning or above. CHANGELOG has an Unreleased Fixed entry.
