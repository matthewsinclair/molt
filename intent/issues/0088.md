## Design (B)

A value fixed when `molt upgrade` renders would go stale at the next login after a `ccusage use`, and Molt's doctor would fail after every switch. So the value is read where it is used, from one definition:

1. The env writer, `lib/env.sh`, takes a third scope beside `all` and `gui`: `command`, whose value is a command line, each word quoted by the writer. env.sh at each shell start and the LaunchAgent at each login set the variable to what the command prints, and unset it when the command fails or prints anything but an existing directory, so a value inherited from launchd or a parent shell cannot outlive the command's answer, and output from another program of the same name is never exported (ccusage-vc, 4 Nov). environment.d cannot run a command, so a Linux sleeve's GUI file leaves it out. The session check leaves the value to the tool that owns it, so doctor never fails on a switch.
2. The claude liberator gives `CLAUDE_SECURESTORAGE_CONFIG_DIR` as a command pair, `ccusage dir` by ccusage's absolute PATH entry, never the Cellar path a link resolves to, on a sleeve where ccusage is on PATH and `CLAUDE_CONFIG_DIR` is published. `MOLT_CCUSAGE`, when set, names the program instead, and an empty one names none, which is how every test starts.

env.sh's line, which `~/.zshenv` sources into every zsh:

```sh
if _molt_env_v="$('/opt/homebrew/bin/ccusage' 'dir' </dev/null 2>/dev/null)" && [ -d "$_molt_env_v" ]; then export CLAUDE_SECURESTORAGE_CONFIG_DIR="$_molt_env_v"; else unset CLAUDE_SECURESTORAGE_CONFIG_DIR; fi; unset _molt_env_v
```

The LaunchAgent's script runs the same shape with `launchctl setenv` and `launchctl unsetenv`. The shell half comes through env.sh, so Molt-matts needs no line of its own, and env.sh and the agent cannot drift apart. Both halves unset the variable until hv's step 1 turns shared mode on.
