## What happens

On kovacs (Ubuntu 26.04.1, kernel 7.0.0-38-generic, bubblewrap 0.11.1 from the distro), Claude Code's Linux sandbox cannot run a command. dc's credentials harness, run A, 21 Oct 2026: every sandboxed Bash, `echo "$HOME"` included, failed before running with

```
apply-seccomp: write /proc/self/setgroups (nested userns is capability-restricted; caller must provide CAP_SYS_ADMIN): Permission denied
```

So the ops and docs roles, whose fence sets `sandbox.enabled` with `allowUnsandboxedCommands: false`, fail closed on kovacs: safe, and unable to run any shell command. The parts that do not need the sandbox behaved as on rhadamanth (the `Read()` denies refused the probes naming the files; the Read tool was denied on both), and the bubblewrap table for ST0006's fence is still owed.

## Cause (kovacs-sysadm, 21 Oct, read-only)

Ubuntu's shipped AppArmor profile `/etc/apparmor.d/bwrap-userns-restrict`. `profile bwrap /usr/bin/bwrap` allows capability and userns, and sends every child through `pix /** -> &bwrap//&unpriv_bwrap`; `profile unpriv_bwrap` allows userns but carries `audit deny capability,`. The sandbox creates a nested user namespace inside bwrap and then writes `/proc/self/setgroups` and `uid_map`, which needs `CAP_SYS_ADMIN` in that namespace, and the deny refuses it. Shown directly: `bwrap --unshare-user --unshare-pid --ro-bind / / --dev /dev --proc /proc unshare -U --map-root-user true` fails with `write failed /proc/self/uid_map: Operation not permitted`, and the kernel log records `apparmor="DENIED" operation="capable" profile="unpriv_bwrap" comm="unshare" capability=21 capname="sys_admin"`. A bwrap child's `/proc/self/attr/current` reads `bwrap//&unpriv_bwrap (enforce)`. The same `unshare` outside bwrap fails too, under `unprivileged_userns`: `kernel.apparmor_restrict_unprivileged_userns = 1` and `kernel.apparmor_restrict_unprivileged_unconfined = 1`. `/etc/apparmor.d/disable/` does not exist; nothing is disabled. The Claude Code native install ships no `apply-seccomp` binary on disk, so the helper is embedded in the binary.

## Why the obvious fix does not work

The profile offers `include if exists <local/unpriv_bwrap>`, but an AppArmor `deny` is evaluated before, and takes precedence over, any `allow`, so a local include cannot grant `capability sys_admin` back. The sysctl alone does not help either: the `bwrap` profile attaches on exec of `/usr/bin/bwrap` whatever the sysctl says, and the children stay under `unpriv_bwrap`.

## Options, hv's host hardening decision

1. **A Molt-managed replacement of the shipped profile**: Molt renders its own `/etc/apparmor.d/bwrap-userns-restrict` (a dpkg conffile, so a package update would ask) in which `unpriv_bwrap` denies every capability but `sys_admin`, or allows `sys_admin` and drops the blanket deny, then `apparmor_parser -r`. Narrow: only bwrap's children gain it, and only that one capability. It is a copy of a distro file with one rule changed, which Molt would then own on every Linux sleeve that runs ops or docs.
2. **Disable `bwrap-userns-restrict` and set `kernel.apparmor_restrict_unprivileged_userns=0`**, both through Molt. Broad: every unprivileged program on the sleeve may then create namespaces with capabilities inside them, which is the hardening Ubuntu added these for.
3. **Leave it**: ops and docs stay fenced and shell-less on Linux sleeves until a later thread; the guide says so.

Either 1 or 2 is a root-owned file written through sudo, which ST0006 WP06 is adding to Molt (`lib/molt.sh` helpers, agents liberator); this change should reuse those, not add a second sudo write path. Scope: Linux sleeves whose manifest enables an ops or docs agent (kovacs today). Then dc's `kovacs-creds.sh` runs A and B for the bubblewrap table, and the guide's "still owed" sentence goes.

## Experiment and route (22 Oct 2026)

hv ran kovacs-sysadm's reversible experiment at the `!` prompt in kovacs-sysadm's session: `priority=1 allow capability sys_admin,` written to `/etc/apparmor.d/local/unpriv_bwrap`, `apparmor_parser -r` on the profile, the bwrap probe, then the undo under an EXIT trap. The parser accepted the rule (reload rc 0) and the kernel replaced both profiles, but the probe failed exactly as before and the kernel logged the same denial after the reload:

```
unshare: write failed /proc/self/uid_map: Operation not permitted
apparmor="DENIED" operation="capable" class="cap" profile="unpriv_bwrap" comm="unshare" capability=21 capname="sys_admin"
```

kovacs was left as found: no local include, and the conffile's sha256 unchanged (`d61facde...1990`). On AppArmor 5.0.2 with kernel 7.0.0-38, a priority-1 allow does not outrank `unpriv_bwrap`'s `audit deny capability,`. A higher priority value was not tried and changes nothing about the ordering, since 1 already exceeds the deny's default of 0; either priority is not applied to capability rules under this profile's abi and kernel, or an explicit deny wins regardless.

**Route: the conffile copy, as the spec above says.** Molt owns `/etc/apparmor.d/bwrap-userns-restrict`: the template rendered with the sidecar first, the distro file kept once as `.molt-orig`, the reload checked and named on failure, the orig restored on removal. A local include is not a route on this release. The template's `unpriv_bwrap` carries `capability sys_admin,` and `audit deny capability <the other forty, by name>,`, the form cc proved parses with `apparmor_parser -Q -K -I /etc/apparmor.d`; the template's head says why the denies are written out. The dpkg conffile cost (a prompt when the apparmor package next changes the file; keep Molt's copy, and `molt upgrade` re-checks it byte for byte) goes in dc's guide section.
