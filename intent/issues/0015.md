Found by critic-shell while reviewing the fix for issue 0013 on 16 Oct; not reproduced live.

`editors_upgrade` pulls the Doom config with `git pull --ff-only 2>/dev/null`, and on failure warns "Doom config pull skipped (not on tracking branch or already up-to-date)". `_upgrade_pull_repos` does the same for the framework and the user config repo. Two things are wrong with that:

- "already up-to-date" cannot be the cause. An up-to-date pull exits 0, so this branch only runs on a real failure.
- git's actual reason (no network, diverged history, local changes in the way) goes to /dev/null, and the upgrade carries on as if nothing happened. That is the issue 0013 shape: a failure reported as a skip, and the sleeve then called ready on a tree that was never updated.

Not fixed with 0013, because what an offline `molt upgrade` should do is a decision. It could stop, or run the hooks against the trees it has and fail at the end. The obvious fix: let git's stderr through, keep the warning only when there is no upstream (`git rev-parse --abbrev-ref '@{upstream}'` fails), and treat every other pull failure as a failure.
