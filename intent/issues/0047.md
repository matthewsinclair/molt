On Linux, Molt's liberators run whichever `gsettings` comes first on PATH. On kovacs that is Homebrew's (glib 2.90.1, pulled in by Elixir's wxwidgets/gtk+3 dependencies, at /home/linuxbrew/.linuxbrew/bin/gsettings), and it has no dconf GIO module: its lib/gio/modules is empty. Instead of reaching dconf, it silently falls back to the keyfile backend at ~/.config/glib-2.0/settings/keyfile, which GNOME never reads.

Reported by kovacs-sysadm, 24 Oct:

- Repro: `XDG_CONFIG_HOME=/nonexistent gsettings get org.gnome.mutter overlay-key` prints 'Super', but `dconf read /org/gnome/mutter/overlay-key` prints ''.
- `molt doctor` reported editors, alacritty, desktop, tiling and vscode as "not installed". It was reading schema defaults while dconf held the right values.
- The next `molt upgrade && molt maintain` wrote those values into the keyfile, so doctor passes now. The keyfile is a second store, though, and it diverges from dconf as soon as anyone changes a setting in GNOME.

Callers: liberators/desktop.sh, alacritty.sh, gnome-terminal.sh and tiling.sh. Each calls bare `gsettings` and guards on `command -v gsettings`. issue 0043 added `_desktop_gsettings_available`.

Fix (vc's direction):
- One helper owns `gsettings` on Linux (Highlander). Every caller goes through it.
- The helper chooses a gsettings whose backend is dconf, and refuses by name when the only one on PATH would use the keyfile or memory backend. That refusal counts as a fault, never as "not installed".
- Doctor names a gsettings without a dconf backend.
- Detect the backend by asking the binary, not by trusting a path. Don't hardcode /usr/bin/gsettings as the answer.
- Tests fake both binaries.

Reordering PATH on kovacs is hv's decision. Once the fix is in, deleting kovacs's keyfile is a separate step, on hv's go, through kovacs-sysadm.
