Found on kovacs, 30 Oct 2026, by rhadamanth-sysadm, read only.

**What happens.** The env liberator writes `~/.config/environment.d/molt.conf` (24 Oct 22:17) with `CLAUDE_CONFIG_DIR` and the login shell's PATH: `/home/matts/.local/bin:/home/linuxbrew/.linuxbrew/bin:/home/linuxbrew/.linuxbrew/sbin:/usr/local/sbin:...:/snap/bin:/home/matts/.cargo/bin:/home/matts/bin:/home/matts/.config/emacs/bin`. The systemd user manager has read the file, because `systemctl --user show-environment` holds its `CLAUDE_CONFIG_DIR`. But its PATH is not molt.conf's: `/home/linuxbrew/.linuxbrew/bin:/home/linuxbrew/.linuxbrew/sbin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin:/usr/games:/usr/local/games:/snap/bin:/snap/bin`. Linuxbrew is there, but `~/.local/bin` is not first and is not there at all, the trailing cargo, bin and emacs directories are gone, and `/snap/bin` is listed twice. So something after environment.d sets PATH again, perhaps an `import-environment` from the GNOME session or another generator.

**Who it reaches.** Every GUI app and user service on kovacs gets that PATH, so none of them finds a tool's `use dev|opt` link in `~/.local/bin` (devbin T5, "your links first"). Herdr does not: its core is started over ssh and gets the environment of ssh's `zsh -c`, which Molt-matts a308e92 fixed.

**Asks.**
1. Find what sets the manager's PATH after environment.d on kovacs (Ubuntu ARM64, GNOME), and make molt.conf's PATH the one the manager holds, or say why it cannot be.
2. The env check on Linux reads the PATH the manager holds (`systemctl --user show-environment`) and names a difference from molt.conf's, as issue 0072 asks of macOS's GUI domain.

Read-only probes on kovacs go through kovacs-sysadm. A test must not compute its expected value with the code under test.


## Cause (molt-vc's read-only probe of kovacs, 30 Oct 2026)

GNOME 50 overrides environment.d at each login. `gnome-session` relaunches itself through `$SHELL` as a non-interactive login zsh (`-zsh -c`), which reads zshenv and zprofile but never zshrc. `gnome-session-init-worker` then uploads that shell's whole environment into the user manager, and systemd keeps uploaded values over what the generators give.

kovacs's GNOME session began on 22 Oct. That was before molt.conf (24 Oct), and before zprofile put `~/.local/bin` first (Molt-matts 91a71ff, pulled 24 Oct). So the manager holds 22 Oct's login-shell PATH: Linuxbrew from `brew shellenv` in front of PAM's /etc/environment, with snapd's `990-snapd.conf` adding `/snap/bin` a second time.

The `CLAUDE_CONFIG_DIR` in show-environment came with the upload, from zshenv, so it does not show that the manager read molt.conf.

Ruled out:
- any other user-environment generator (there is none);
- environment.d's order and syntax (molt.conf wins in the generator's output);
- profile.d;
- user units;
- X11's `dbus-update-activation-environment` (this session is Wayland).

## Fix

1. Molt cannot win from environment.d, because the upload comes after it, and Molt sets nothing through systemctl. The fix is the sleeve's zsh config, in Molt-matts `config/zsh/`:
   - zprofile gains `typeset -U path PATH` before its brew block. `brew shellenv` skips its prepend only when PATH already starts with the Linuxbrew pair, so a seed with `~/.local/bin` first would gain the pair again at every login. The same line collapses the doubled `/snap/bin`.
   - zshrc's `path_add` lines for `~/.cargo/bin`, `~/bin`, `~/.config/emacs/bin` and `~/.mix/escripts` move into zprofile, after `path_prepend ~/.local/bin`.

   The login shell GNOME runs then builds molt.conf's PATH exactly. The change takes effect at the next GNOME logout and login on kovacs; linger is on, so the manager survives the logout. Land it on kovacs before that login: today's zprofile exports `MOLT_ZPROFILE_RAN=1`, which would be uploaded with the short PATH, and non-login shells in that session would then skip zprofile.
2. Molt: on Linux, doctor's env check reads `systemctl --user show-environment` and names each published pair the manager holds differently (ask 2, built with issue 0072's ask 1). `_molt_env_conf_text`'s comment no longer says that under GNOME every GUI child sees environment.d's values.

## Proof

Before the re-login, this prints what the next login will upload: `env -i HOME=$HOME USER=$USER LOGNAME=$USER SHELL=/usr/bin/zsh TERM=dumb PATH="$(systemctl --user show-environment | sed -n 's/^PATH=//p')" zsh -lc 'print -r -- $PATH'`.

After the re-login:
- `systemctl --user show-environment | grep '^PATH='` equals molt.conf's PATH line, with one Linuxbrew pair and one `/snap/bin`;
- gnome-shell's environ holds the same line;
- show-environment holds `MOLT_ZPROFILE_RAN=1`, which shows that the new zprofile made the upload.


## As built, Fix 2 (dc, 30 Oct 2026; merged by vc at 4ede53c, with issue 0072's ask 1)

- `lib/env.sh`: on Linux, `molt_env_report_session` reads `systemctl --user show-environment` (`_molt_env_systemd_vars`, pure) and names each published pair the manager does not hold, or holds with another value. A value systemctl prints as `NAME=$'value'` with nothing escaped inside is read back as the value; molt refuses `\` and `'` in what it publishes. The remedy it gives is to log out and back in after `molt upgrade`; it never runs `systemctl set-environment`. A `systemctl` that fails is reported and fails the check. `_molt_env_conf_text`'s header no longer says that every GUI child sees environment.d's values, so an existing molt.conf reads as not what molt would publish until `molt upgrade` renders it again.
- Tests (`test/liberators/env.bats`): a fake user manager prints an upload or molt.conf's lines. The check names a different PATH and a missing prefix, passes on a match, reports a manager it cannot read, and reads back a quoted value with a space in it. Each failed before its fix, under bash 5.3 and /bin/bash 3.2.
