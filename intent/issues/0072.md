Found on gyges, 28 Oct 2026 (macOS 27.0.1, molt 1.1.0 brew b9d59e2), by gyges-sysadm, and confirmed by hv running `molt doctor` in his own iTerm window at 15:40.

**What happens.** `molt doctor` fails its env-liberator check with "launchd does not hold CLAUDE_CONFIG_DIR / PATH", even with com.molt.env.plist loaded (`launchctl bootstrap gui/501 ~/Library/LaunchAgents/com.molt.env.plist`, exit 0):

- `launchctl print gui/501` holds both PATH and CLAUDE_CONFIG_DIR, as the agent published them.
- `launchctl print user/501` holds neither.
- `launchctl getenv <name>` comes back empty, both from a Background-domain session and from hv's terminal.

`molt_env_report_launchd` (lib/env.sh, around line 356) reads with `launchctl getenv`, so on gyges it can't see what the agent set.

**rhadamanth differs.** On the same macOS 27.0.1, `launchctl getenv CLAUDE_CONFIG_DIR` answers there, and `launchctl print gui/$UID` holds both. So getenv's answer depends on the session or on how the values got set: at login, or by a bootstrap after login. It isn't a plain macOS 27 break. The check has to read the domain the agent writes to.

**A second, separate question.** Conflab.app, started on gyges at 15:37 after the bootstrap, got CLAUDE_CONFIG_DIR, but its PATH was launchd's default (/bin:/sbin:/usr/bin:/usr/sbin:/usr/libexec). So `launchctl setenv PATH` may not reach GUI apps on macOS 27 at all, even with the agent loaded.

**Asks.**
1. The doctor check reads `launchctl print gui/$UID`, not getenv, so it reports what launchd's GUI domain actually holds.
2. Verify whether PATH set by the env agent reaches a GUI app launched afterwards on macOS 27. If it doesn't, doctor says so plainly instead of offering the bootout/bootstrap remedy.

A test must not compute its expected value with the code under test (see Molt's test rules).


## As built, ask 1 (dc, 30 Oct 2026; merged by vc at 4ede53c, with issue 0076's ask 2)

- `lib/env.sh`: `molt_env_report_session` replaces `molt_env_report_launchd`. On macOS it reads `launchctl print gui/<uid>` once and parses the domain's environment block (`_molt_env_launchd_vars`, pure), so it reports what launchd's GUI domain holds; no per-name `launchctl getenv` is left. A `launchctl print` that fails is reported and fails the check. The macOS messages and the bootout/bootstrap remedy are unchanged. molt-vc checked the parser against rhadamanth's real `launchctl print gui/501`.
- Tests (`test/liberators/env.bats`): the fake launchd answers `print` as launchd does, and its getenv can answer nothing, as on gyges; the check passes there. It failed before the fix, under bash 5.3 and /bin/bash 3.2.


## Ask 2, answered on rhadamanth (dc's probes, 1 Nov 2026; vc confirmed)

dc ran two read-only lights on devbin-vc's desk, with nothing launched and no root, and wrote each one's expected verdict down before its slot was asked.

- Slot 01M6B904306VPQQ9VNZMR445D4: `ps -wwE` couldn't read Xcode's environment (pid 52011, parent launchd, started 06:29:24Z on 1 Nov, nine hours after the 21:31Z login), and no other app was tried, so this slot gave no verdict.
- Slot 01M6B9H0N3522P9DBZZMR48CS3: launchd's record of Xcode's job (`launchctl print gui/501/application.com.apple.dt.Xcode.*`, submitted by runningboardd). The job inherits the domain's PATH and CLAUDE_CONFIG_DIR, both byte-identical to those in `launchctl print gui/501`. Its default environment is PATH => /usr/bin:/bin:/usr/sbin:/sbin. Its own environment sets CLAUDE_CONFIG_DIR to the domain's value, and PATH to launchd's default with /Applications/Xcode.app/Contents/Developer/usr/bin in front. launchctl(1) gives a service's own PATH precedence, so Xcode runs with none of the domain's PATH.

Answer: the PATH the env agent publishes does not reach GUI apps on macOS 27, and CLAUDE_CONFIG_DIR does. Two apps agree: Xcode on rhadamanth (macOS 27.2, the agent loaded at login, on launchd's record) and Conflab on gyges (macOS 27.0.1, the agent bootstrapped after login, in the process itself). Two questions stay open, and the fix needs neither answer. One is whether an app job with no PATH of its own would take the inherited PATH. The other is how far an app's own PATH depends on how it was opened: Xcode's has the shape xcrun gives a tool run from launchd's default PATH, and its Info.plist declares no LSEnvironment.

Owed, and held with 0078 until Molt's next release (vc decision 35: Molt is held for code). On macOS, doctor's env check says plainly that GUI apps don't get the PATH Molt's agent publishes, instead of offering the bootout/bootstrap remedy for it.
