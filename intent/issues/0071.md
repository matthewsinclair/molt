## What

The pplr liberator can only link the dev checkout: it always links `$MOLT_LOCAL_BIN/pplr` to `$MOLT_PPLR_HOME/bin/pplr` (`liberators/pplr.sh:45`). On rhadamanth that is `~/.local/bin/pplr -> ~/Devel/prj/Pplr/bin/pplr`. pplr is to move to Homebrew later (hv, 27 Oct), and once it has a formula the liberator needs to install that instead when a sleeve's manifest says so.

hv, 27 Oct 2026, verbatim: "We need to move pplr to brew too, but not now. So Molt needs to be able tp handle either. It shouldn't be a rule that Molt only does this one way or the other. Molt does what it's told and if its a local symlink to a dev checkout in the Molt config, then that's perfectly ok. Molt shouldn't judge that. But what we are doing now with molt, devbin, utilz, gtools, conflab, laksa, is building brew installs for those tools because they need it."

## Next

1. Give the pplr liberator a `source` choice in the sleeve's manifest, brew or checkout, as the utilz liberator has (`_utilz_source`, `liberators/utilz.sh:24`). Checkout keeps today's link; brew checks and installs the formula.
2. Molt does what the manifest says and judges neither choice: no check warns about a configured link into a dev checkout.
3. The brew half waits for a pplr formula. Until then every sleeve stays on checkout, as now.

## Not this issue

The first version of this issue, filed the same morning, read hv's earlier rule about links into dev checkouts (relayed by utilz-vc after it removed `~/.config/menuz/bin/arngz`) as applying to Molt's own links. hv's words above correct that: a link Molt makes because its config says so is fine. The utilz liberator's checkout mode stays as it is.

Molt's builders start only when hv calls Molt.
