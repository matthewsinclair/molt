## [Unreleased]

### Added

- `[[agent]]` entries in a sleeve's molt.toml declare its sleeve agents, the local agents that do machine work on it as the user: `role` (required), `enabled` (default true) and `harness` (default and only value `claude`). An agent's name is derived, never written, as `<hostname>-<role>`, so the convention cannot be mistyped. An entry with no role, a role declared twice, a written name, or another harness is reported rather than read (ST0006)
- `agents` liberator renders each enabled agent's home at `$MOLT_AGT_DIR/<name>` from the user repo's `config/agents/roles/<role>/`. It writes `AGENTS.md` from three layers in order: the user repo's role-independent `config/agents/AGENTS.md.tmpl` when it has one, which holds what every sleeve agent is told and no role template repeats (AC016); the role's `AGENTS.md.tmpl`; and the sleeve's overlay `instances/<host>/agents/<role>.md` when it has one: host facts true of that machine only, which a role's template, one file for every host, cannot hold. A changed, added or removed preamble or overlay makes the home stale. It writes `CLAUDE.md` as an `@AGENTS.md` import, and `.claude/settings.json` from `settings.json.tmpl` with `autoMemoryDirectory` set to the home's `memory/`, so an agent's memory travels with its home. A settings template that does not render to one JSON object, an empty or `null` one, or two objects, included, fails the install and leaves the file as it was. Each file of a home is built whole, its layers and settings.json's memory dir included, before it is compared with what is on disk, so a re-render that would write a file as it is backs nothing up, and a layer that cannot be rendered leaves the file as it was. It creates `memory/` and `work/`, which are the agent's and which molt never writes into. `MOLT_HOSTNAME`, `MOLT_AGENT_NAME`, `MOLT_AGENT_ROLE` and `MOLT_AGENT_HOME` are there for the templates. Digest sidecars decide re-rendering, overlay included, so a re-render while they match writes nothing. A role the user repo does not define is a fault naming the role and the path looked in. Rendering a home waits on nothing the `claude` liberator does, so a live agent can copy its files in before its state moves (ST0006)
- `molt agent list` prints each declared agent with its role, whether it is enabled, the state of its home (current, stale, not rendered, role undefined) and the home. `molt agent config <name>` prints its home, each rendered file's state, the settings files Claude Code reads for a session there, highest first, and every `permissions` rule in effect, deny first, each tagged with its layer: managed (`managed-settings.json` and its `managed-settings.d/` drop-ins), local (the home's `settings.local.json`, where Claude Code records approvals), home, and user. An undeclared name fails, listing the declared ones. Reading the rules needs jq, and a missing jq is named (ST0006)
- `MOLT_AGT_DIR`: where sleeve agents live, the `agt/` sibling of `MOLT_PRJ_DIR` as `MOLT_CFG_DIR` is the `cfg/` one, so `~/Devel/prj` gives `~/Devel/agt`, the value the user repo's zshenv gives shells; empty, rather than a guess, when `MOLT_PRJ_DIR` is not set either. It is exported, so the `claude` liberator's home guard is rendered with it. `molt_agt_dir_fault`, which both the `agents` and the `claude` liberator ask before anything is written, refuses a root that is empty ("MOLT_AGT_DIR cannot be resolved: MOLT_PRJ_DIR is unset"), relative, not canonical, or holds a line break; one at or above `$HOME`, `MOLT_PRJ_DIR` or `MOLT_CFG_DIR`, where the guard would refuse every project, compared as the disk spells them, as the guard compares them, so a symlink or another letter case is no way round; one at or under `~/.claude`, Claude Code's config dir, or the config dir the sleeve declares; and one that a sleeve's `vars.sh` sets, appends to or unsets, since `vars.sh` is sourced with `MOLT_AGT_DIR` already exported when the guard renders. A root derived from `MOLT_PRJ_DIR` is named so in a refusal (ST0006)
- `claude` liberator's home guard also refuses a session launched under `MOLT_AGT_DIR` but not in an agent home itself, the agents root or anything below a home, and names the home to launch from. Claude Code reads `CLAUDE.md` up the tree but project settings only from the launch directory's `.claude/`, so a launch below a home kept its contract and lost its fence. A session launched in a home, or outside the root, passes. The root is rendered into the guard as it stands, from a quoted here-document, so no character in it is syntax there; check reports a guard rendered with a root that is no longer `MOLT_AGT_DIR`, which install then renders again. The guard compares directories as the disk spells them, with `/bin/pwd -P`: bash's own `pwd -P` keeps the letter case it was given, and on a disk that ignores case a root spelt otherwise fenced nothing (ST0006 AC014)
- `molt_claude_managed_dir`: where Claude Code reads managed settings on this platform (ST0006)
- `molt_render_text` and `molt_render_place`: `molt_render` in two halves. The first renders a template into a file with this sleeve's `vars.sh`, and nothing more, and names a missing envsubst; the second puts a render in place: the region kept above `@@MOLT:BEGIN@@`, the backup of a file that differs from what molt would write, the region kept above the marker included, and the sidecar, whose digest covers the extra inputs its caller built in. The `agents` liberator builds each home file whole between the two (ST0006)
- `molt_disk_path`, `molt_path_fault` and `molt_agt_dir_derived`: a path as the disk spells it, resolved as the `claude` liberator's home guard resolves it; the absolute-and-canonical check the `claude` liberator and `molt_agt_dir_fault` share; and the agents root `constants.sh` derives from `MOLT_PRJ_DIR` (ST0006)
- `claude` liberator moves Claude Code's state out of `$HOME` on a sleeve whose `vars.sh` declares `MOLT_CLAUDE_CONFIG_DIR`, and changes nothing on one that does not, so hv arms the move sleeve by sleeve. Once, and only while no Claude Code runs, it copies `~/.claude` and `~/.claude.json` beside the config dir (an APFS clone on macOS) and moves both into it. It refuses, naming the processes, while any Claude Code is running, the session molt was started from included (macOS's `pgrep` leaves out its own ancestors unless given `-a`), because a live session cannot survive its own state moving. It refuses a config dir that already holds anything, naming its contents, and never merges the two. It will not publish a newly declared, empty dir while `CLAUDE_CONFIG_DIR`, in the shell or in `env.sh`, names another dir that exists, where the state may still be. Only once the state is there does it write `~/.config/molt/env.sh`, which `~/.zshenv` sources to set `CLAUDE_CONFIG_DIR`, and the GUI environment (`~/Library/LaunchAgents/com.molt.claude-config-dir.plist` on macOS, `~/.config/environment.d/claude.conf` on Linux). A variable published before the move would start the next Claude empty in the new dir, and the move would then meet a dir that is not empty. It refuses a declared value it cannot write as it stands, rather than rewriting it: a relative or non-canonical path (a trailing slash, `//`, `.` or `..`), a quote, `$`, a backtick, a backslash, `<`, `>` or `&`, or trailing whitespace, which environment.d strips. It refuses a `vars.sh` that cannot be read, does not parse or stops before its end when sourced, which had read as declaring nothing and on a moved sleeve recreated `~/.claude`, and a declared value with a line break in it, which `$()` would have cut from its end while `env.sh` kept it. After any refusal neither file is written, and nothing else is changed (ST0006)
- `claude` liberator refuses a Claude Code session launched in `$HOME` on such a sleeve: a `UserPromptSubmit` hook in the user `settings.json` runs `~/.config/molt/claude-home-guard.sh`, which exits 2 with "launch from an agent home: molt agent list" when the session was launched in `$HOME` and passes any other. It reads where a session was launched from `CLAUDE_PROJECT_DIR`, which stays put when the session cds or enters a worktree, not from the hook input's cwd, which follows every cd. It needs nothing beyond sh, and exits 1, which blocks nothing but says so, when the hook has no `CLAUDE_PROJECT_DIR` or `HOME`, or one that is not absolute, which `cd` would resolve against wherever the hook runs. It joins every other `UserPromptSubmit` entry, which molt keeps. The statusLine and the hook go into `settings.json` through one merge that changes no other key (ST0006)
- `claude` check and verify, so `molt doctor`, report on such a sleeve: `CLAUDE_CONFIG_DIR` unset where molt runs, or naming another dir; `~/.claude` or `~/.claude.json` present, as a directory, file or link, while the config dir is elsewhere, which is the sign that a launch path missed the variable; a move still pending; and `env.sh`, the GUI file or the guard missing, stale or not executable, or the hook missing from `settings.json`. The native installer's own `~/.local/{bin,share,state}/claude` and `~/.cache/claude` are not faults (ST0006)
- `claude` liberator links `config/claude/CLAUDE.md` and `config/claude/AGENTS.md`, the user-scope rules every session on the sleeve reads, into the config dir when the user repo has them, as it links `keybindings.json`. A regular file already there is backed up first (ST0006)
- `molt_claude_config_dir`: where Claude Code keeps its state, `CLAUDE_CONFIG_DIR` or `~/.claude`. Every path the `claude` liberator reads or writes goes through it; five were hardcoded to `~/.claude`, and its `mkdir -p "$HOME/.claude"` would have recreated exactly what doctor faults (ST0006)
- `molt_instance_vars_fault`, `molt_instance_var` and `molt_instance_vars_file`: why this sleeve's `vars.sh` cannot be sourced; a variable as the file exports it; and the file's path, which `molt_render` and `molt_config_digest` had each worked out for themselves. `molt_render` and `molt_instance_var` are the two places that source the file, each in its own subshell so a `declare -x` in it stays in scope, and both ask `molt_instance_vars_fault` first; the `claude`, `tiling` and `backup` liberators and doctor's font check read through `molt_instance_var`. A `vars.sh` that cannot be read, does not parse, or stops before its end when sourced (a `return` or an `exit`, or an error under a `set -u` or `set -e` of its own, caught alike under bash 3.2 and 5 by sourcing a copy that answers from its last line in a fresh bash) is refused, saying which, rather than reading as though it declared nothing after the point it stopped at; so is a value with a line break or carriage return in it. `molt_instance_var` says why for every failure (ST0006)
- `molt_hostname`: this sleeve's short hostname, which names its `instances/` directory, cut at the first dot, and a failure when the host gives no name; such a host takes the repo-level `molt.toml`. `lib/molt.sh`, `bin/molt`, `tiling` and `backup` had worked it out seven times; the other liberators' six copies are issue 0020 (ST0006)
- `molt_render_stale`: `molt_config_stale` for a template named by its path, as Molt's own templates under `templates/` are. It fails closed, a missing template included; `molt_config_stale` now asks it once it has found the user repo's template (ST0006)
- `docs/guides/sleeve-agents.md`: the guide to sleeve agents, a machine's local agent given a home of its own. It covers how a sleeve agent differs from a project agent; the `<hostname>-<role>` name, the host naming scheme and the six project-Claude suffixes; the `sysadm`, `ops` and `docs` roles; the three layers and what a session in a home reads; declaring an `[[agent]]` and what Molt renders into its home; `molt agent list` and `molt agent config`; moving Claude Code's state out of `$HOME` once per sleeve, with every session quit first; what `molt doctor` reports; and the fence and the wall (ST0006)

- `utilz` liberator takes Utilz from a checkout or from Homebrew, as each sleeve declares with `source = "checkout"` (the default) or `source = "brew"` on its molt.toml entry. In brew mode install runs `brew install matthewsinclair/utilz/utilz` and links nothing, and upgrade leaves it to brew, because utilz's own upgrade, relink and use refuse inside the keg. In either mode check and verify name the utilz that PATH runs, and every utility beside it that runs from elsewhere. kovacs is brew-only by hv's ruling, and its check said "repo not found" over a working install (ST0005)
- `molt_liberator_field`: a liberator's own key, read from its entry in this sleeve's molt.toml. It, `molt_enabled_liberators` and `molt list` read molt.toml's `[[liberator]]` blocks through one parser, `_molt_liberator_entries`; there had been three. A key now counts wherever it sits in its entry, a key below a later table belongs to no entry, and `enabled` is read from its value, so a comment on the line that says "false" no longer disables a liberator. Every instance manifest in the user repo gives the same liberators as before, on linux and macos (ST0005)
- `molt_brew_faults`, `molt_brew_install`, `molt_path_runs_fault`, `molt_path_misses`, `molt_report_faults` and `molt_cmd_version`: the Homebrew check, written once in `lib/molt.sh`. `intent` had its own copy and now uses these, with its tests unchanged; `utilz` needed the same answers (ST0005)
- `molt_same_file`: true when two paths resolve to the same file, the comparison `molt_link_points_to`, the Homebrew check and intent's gate check had each written out (ST0005)
- `fake_brew_formula` in `test/test_helper.bash`: a Homebrew prefix and brew stub in the test directory, trust gate included, for testing any Homebrew liberator. `list` answers only for its own formula, and every call that would change Homebrew is logged. `intent.bats` uses it too, so its tests now see how intent asks Homebrew (ST0005)

- `[terminal] bg_color` in a sleeve's `instance.toml`: its own iTerm2 background. The generated ssh wrapper resets a tab to it when ssh returns, rather than to black; a sleeve without one still resets to `000000`. xterm's OSC 111 reset does not undo iTerm2's `SetColors`, so the colour has to be declared (issue 0012)
- `claude` liberator manages the Claude Code status line. It links `~/.config/ccstatusline/settings.json`, the ccstatusline layout, from the user repo, and writes only the `statusLine` key of `~/.claude/settings.json` from `config/claude/statusline.json`, keeping every other key and the file's mode and backing up the file it replaces. `settings.json` itself is never linked: it holds each sleeve's own permissions, hooks and plugins. check and verify report a link that is missing, broken or points elsewhere, and a statusLine that differs; key order is not a difference. On 15 Oct another tool replaced rhadamanth's statusLine and molt could not put it back, because the liberator linked only `keybindings.json`. The merge uses jq, which `dev-tools` already requires (issue 0009)
- `molt_report_link_faults` and `molt_link_all`: the check, install and verify loops over a liberator's list of user-repo links, written once in `lib/molt.sh`. `git` had its own copies and `claude` needed the same; the copies had already drifted. A link that resolves somewhere else now names the source it should point at. It used to say "not the user repo", which was false for a link to another file inside the repo
- `molt_config_stale` and `molt_config_digest`: liberators that render configs can now detect when a rendered file no longer matches its inputs. molt renders only when a `_check` reports not-ok, so before this a template change never propagated -- the check passed, install was skipped, and the sleeve ran the previous rendered file while reporting success. Wired into `ssh`, `zsh` and `backup`, the three liberators that render
- `molt doctor` check (11th): the stack itself must be on local storage. Rejects `fuse*`, `nfs*`, `smb*`, `cifs`, `9p`, `virtiofs` and friends. Catches a sleeve running out of another machine's checkout over a guest or network mount, which check 10 cannot see because the coupling is structural rather than textual
- `claude` liberator: owns `~/.claude/keybindings.json`. It was version-controlled in the user repo but no liberator created it, so it existed only where it had been linked by hand and a fresh sleeve never got it
- `desktop` liberator manages GNOME dock favourites from `instances/<host>/desktop/favorite-apps` (one `.desktop` id per line, order = dock order). A file that is present but yields no entries is refused with a warning rather than applied -- applying it empties the dock, and that is far more likely to be a malformed file or a glob that matched nothing than a deliberate bare dock. The dock silently outranks every default-terminal setting: a sleeve with alacritty set as default by both gsettings and `/etc/alternatives` still launched gnome-terminal, because both were pinned and the icon was what got clicked
- `desktop` liberator links `gtk-4.0/gtk.css` as well as `gtk-3.0`. GTK4 apps are now the common case, and molt could not repair a gtk-4.0 link because it never created one
- `molt_link_points_to`: true only when a link resolves _to the expected source_. `molt_link_healthy` asks whether a link resolves, not whether it resolves to what the liberator installs
- `molt doctor` check (12th): warns when `core.ignorecase=true` in the managed repos. Framed as a standing condition expected on macOS, with the remedy at rename time (`git mv -f`, then confirm it staged) -- explicitly _not_ "set it false", which would make git assert something untrue about the filesystem in order to silence a check. A case-only rename is then not committed, so a case-sensitive sleeve pulls the old spelling and every symlink to it dangles -- the mechanism that hid the repo rename
- `molt doctor` check 4 now asserts the manifest's `user_repo` still names the real directory. The key is never read by anything, so as prose it drifted silently; asserting it turns dead documentation into a live check
- `editors maintain` warns when straight.el has left dangling links in the ACTIVE build tree. straight adds and updates build-dir entries but never PRUNES ones whose source vanished upstream, so a renamed or dropped file leaves a link pointing at nothing and Emacs dies at boot with a bare `(file-missing ...)`. Runs after `doom sync -u`, which is the only thing that causes it; not in `_check`, where a 6000-entry scan costs ~5s (`find -L` makes it ~60ms)
- `molt_link_healthy` and `molt_link_fault`: symlink checks that test whether a link _resolves_, plus a helper that names which of the four states a target is in for user-facing messages
- `molt_fstype`: filesystem type for a path, branching on platform rather than probing (BSD `stat` reads GNU's `-f -c %T` as a format string and prints `-c` instead of failing)
- `molt_render` honours the `@@MOLT:BEGIN@@` marker its own templates advertise: content above the marker in an existing file is preserved across re-renders. Previously the whole file was replaced, so "add your own entries ABOVE this line" was not true
- `molt upgrade` warns about unpushed commits and untracked files. Unpushed commits are the damaging case: `git pull --ff-only` cannot fast-forward past them, so it is skipped with a soft warning and every other sleeve upgrades to a tree without the fixes while reporting success
- `docs/guides/templates.md`: sections on detecting stale renders and on preserving hand-written entries
- `molt new-user` command: scaffolds a new `molt-{user}` config repo from a tokenised skeleton (`templates/molt-user/`), substituting name, email, GitHub handle, and first hostname. Implemented in `lib/newuser.sh` with `test/newuser.bats` (10 tests)
- `docs/guides/new-user.md` guide explaining the scaffold, the identity surface, and the scaffold-time vs resleeve-time placeholder split
- `git_install` config-linking tests in `test/git.bats` (arbitrary identity name, multiple includes, empty-glob guard)
- `molt doctor` check (10th) for config files that bake in another user's absolute home path, including JSON-escaped `\/Users\/<x>` exports (`molt_foreign_home_paths`)
- `molt doctor` external-dependency check now also verifies `envsubst` (gettext), required for template rendering
- `MOLT_CFG_DIR`: where the user config repo lives, apart from development projects. Defaults to the `cfg/` sibling of `MOLT_PRJ_DIR` (`~/Devel/prj` gives `~/Devel/cfg`) and is searched before `MOLT_PRJ_DIR`, which stays in the search list so a sleeve whose repo has not moved still resolves
- `web` liberator test (`test/liberators/web.bats`)
- `test/liberators/backup.bats`: the `backup` liberator's first tests (31). Fixtures stand in for SuperDuper's state through `MOLT_SD_TILES` and `MOLT_SD_SCHEDULER_LOG`, and the errexit arms run in a fresh `bash` under `set -euo pipefail`, where a failing assignment would abort

- An `npm` liberator keeps npm's cache out of `$HOME`: it renders `~/.npmrc` from `templates/npm/npmrc.tmpl`, naming `${XDG_CACHE_HOME:-$HOME/.cache}/npm` as the cache, so npx, which the status line runs at every refresh, no longer fills `~/.npm` on every sleeve. Lines of the user's above the marker are kept, those of an `~/.npmrc` molt has not rendered among them, the file is mode 600, and verify asks npm which cache it reads. A sleeve with no npm passes with nothing to configure. Nothing removes `~/.npm`: check names it as the old cache, left for the user (issue 0031)

### Changed

- `molt_render` refuses a `vars.sh` that cannot be read, does not parse or stops before its end when sourced, and a render that fails or never ran, and leaves the target as it was. It had rendered what the file exported before a syntax error, or nothing from a file it could not read, and moved a failed render into place; a `vars.sh` that exited as it was sourced left the target backed up with nothing in its place. It is sourced as a profile is, with nounset off and its output discarded: under molt's nounset an unset variable in it had stopped the render, and whatever the file had printed was moved in as the rendered file (ST0006)
- `_molt_liberator_entries` is `_molt_table_entries`, the one reader of molt.toml's array tables: it takes the table and the key that names an entry, so `[[liberator]]` (by `name`) and `[[agent]]` (by `role`) are read the same way. An entry with no such key is now printed with an empty id, so a caller can refuse it rather than never see it; the liberator callers skip it, as before (ST0006)
- A link fault names a target outside `$HOME` by its own path. `molt_report_link_faults` wrote `~` before whatever followed `$HOME`, which named such a target as if it were inside `$HOME`, and Claude Code's config dir may now be anywhere (`molt_tilde`, ST0006)
- `intent` liberator installs Intent from Homebrew (`brew install matthewsinclair/intent/intent`) instead of linking a source checkout's dispatcher into `~/bin`. Its check fails, naming the path, when `intent` on PATH is not Homebrew's, and when the pre-commit gate's home is missing, names an install that is gone, or names another install. On gyges the old check printed ok over a link to Intent 2.6.0 while a login shell ran Homebrew's 3.2.0. `MOLT_INTENT_HOME`, the `~/bin/intent` link and `molt git` over the Intent checkout are gone. Disabled on rhadamanth, where Intent is developed (ST0004)
- `backup` liberator rewritten for SuperDuper 4.0.5, which creates and owns its own sparsebundle on the SMB share. It no longer creates, attaches or detaches the disk image -- anything competing for the image can permanently break the job's destination binding. `maintain` refuses to tear down the share while the image is open. `MOLT_BACKUP_VOLUME` removed; `MOLT_BACKUP_IMAGE` now names the sparsebundle. A missing image is a warning, not an error
- `backup-mount` mounts via NetAuth rather than `mount_smbfs`. `/Volumes` is `root:wheel drwxr-xr-x`, so the previous `mkdir -p` could never succeed as a normal user; it failed silently and the mount only worked when Finder had already created the mount point. Also logs the tool's real stderr, password scrubbed, and trims its log to 30 days
- `editors_maintain` runs `doom sync -u` unconditionally. `doom upgrade` short-circuits before the package sync when Doom itself is current, so packages orphaned by a failed run were never retried while maintain reported success
- `editors_check` warns when `emacs-plus` is linked against ImageMagick, which breaks Emacs at launch on every imagemagick soname bump

- `git` liberator now links any `config/git/gitconfig_*` identity include instead of a hardcoded filename
- `bootstrap.sh` no longer assumes a fixed GitHub owner for the config repo: `MOLT_REPO` and the new `MOLT_USER_GH` are overridable (default `whoami`)
- `bootstrap.sh` clones the config repo into `MOLT_CFG_DIR` as `Molt-{user}`, and uses one it finds already in `MOLT_PRJ_DIR` rather than cloning a second copy. It cloned `molt-{user}` in lowercase, which `molt doctor` then flagged as off-convention
- `molt new-user` scaffolds into `MOLT_CFG_DIR` when `--dest` is not given, and its printed next step sets `MOLT_CFG_DIR` rather than `MOLT_PRJ_DIR`
- Removed hardcoded personal identity strings throughout framework docs and project artifacts; the framework now reads as generic `{user}`/`{github}`
- `molt new-user` skeleton defaults `MOLT_FONT_FAMILY` to `Hack Nerd Font Mono` (a Nerd Font, matching the iTerm2 profile) so the prompt glyphs render out of the box
- `backup_verify` has three exit codes: 0 when every check ran and passed, 1 when a check failed, and 2 when nothing failed but the share-side checks (SMB dialect, attach budget) could not run. 2 is the usual state, because SuperDuper mounts the share only while it copies

### Fixed

- The home-launch guard could not refuse a Claude Code started without the sleeve's config dir, as one started from a shell opened before the move is: such a session starts afresh in `$HOME`, with a second login, and never reads the user settings that ran the guard, which are in the config dir it missed. On kovacs that session ran for seven minutes on new state in `$HOME` before `molt doctor` named it. The agents liberator now writes the same hook entry into each home's `.claude/settings.json` on a sleeve that declares `MOLT_CLAUDE_CONFIG_DIR`, beside the role's own hooks, and project settings are read whatever config dir a session uses. The guard, outside any config dir, is rendered with that config dir too, and exits 2 when the session's `CLAUDE_CONFIG_DIR` is unset or names another directory, compared by where each leads. A home rendered without the hook is stale, and `molt agent config` shows whether its settings run the guard. The claude liberator's check reports a guard rendered with another config dir, or with none, which install renders again. The hook entry and its jq filters are now in `lib/molt.sh`, shared by both liberators (issue 0030)
- The `ssh` liberator linked a static `config/ssh/config` to `~/.ssh/config`, which ssh refuses as a link, and which its own check and verify refused, so the sleeve never settled. It now renders `~/.ssh/config` from `config/ssh/config.tmpl` alone, and check, install and verify refuse a static `config/ssh/config` with no template beside it, saying to rename it `config.tmpl`, which renders it as it stands since only `MOLT_*` variables are substituted, and naming any `config.d` fragments it left unapplied. A repo with both files takes the template, as before. Verify no longer fails a repo with no ssh config and no fragments, which check and install pass, over a `~/.ssh/config` it was never to write (issue 0027)
- A render over a file molt itself rendered backed it up whenever the new render differed, warning that the rendered file had changed since last render, so every template change left a `.molt-backup.<stamp>` in every rendered target, the agent homes among them. The `.molt-rendered` sidecar now records the digest of the file molt wrote as well as of its inputs: a file still as molt wrote it is replaced with no backup, and only a hand edit, or lines above `@@MOLT:BEGIN@@` the new render drops, is backed up with the warning.
